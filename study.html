01What ASD-STE100 is

ASD-STE100 is a controlled natural language. The aerospace and defence industry wrote it for maintenance manuals. Readers across many countries must understand those manuals the same way. The standard became international in 2025.

The standard has two parts that work together.

PartNameWhat it does
Part 1 Writing rules 53 rules in 9 sections. The rules cover words, verbs, sentences, procedures, descriptions, warnings, punctuation, and practice.
Part 2 Dictionary About 900 approved words. Each word has one meaning and one part of speech. About 1200 non-approved words have approved alternatives.

The goal is one word, one meaning, one part of speech. When English has many synonyms, STE picks one. It uses start instead of begin, commence, or initiate. When a word has many meanings, STE picks one. Fall means to move down by gravity. It does not mean decrease.

Key idea

STE is not a style guide. It is a specification. Its rules are testable. Plain English and STE overlap, but they are not the same. Clear text can still break STE rules.

02The core constraints

These are the limits that change writing the most. Learn these first.

ConstraintRuleDetail
Length Sentence limits Procedural: max 20 words. Descriptive: max 25 words. Warnings and cautions: max 20 words.
Length Paragraph limit Max 6 sentences. One topic per paragraph. Start with the topic sentence.
Voice Active voice Always active in procedures. In descriptions, use active as much as you can. Passive only when the agent is unknown or unimportant.
Verbs Six forms only Infinitive, imperative, simple present, simple past, future, past participle as adjective. No progressive, no present perfect, no past perfect.
Verbs Modals Only can and must are approved. Do not use may, might, could, should, would, shall.
Words Controlled vocabulary Use approved words, technical names, and technical verbs. Each approved word keeps its one meaning and one part of speech.
Words Noun clusters Max 3 words in a multi-word noun. Longer terms become phrases with of, on, in, for.
Structure One topic per sentence One instruction per sentence in procedures. Do not omit words to make sentences short.
Punctuation No semicolons Semicolons are banned. All other standard marks are allowed.
Counting Word count rules A number with its unit counts as 1 word. An abbreviation counts as 1. A hyphenated group counts as 1. Parenthetical text counts as its own sentence.

Procedural vs descriptive

STE splits text into two types. Each type has its own rules.

Procedural

Instructions. Use the imperative. Max 20 words. One instruction per sentence. Always active voice. Example: "Tighten the bolt to 25 N·m."

Descriptive

Information about an item or system. Declarative. Max 25 words. Active as much as possible. Paragraphs show logic. Example: "The valve controls the flow of fuel to the engine."

03The 53 rules in brief

Nine sections. Full text lives in the official specification (Issue 9, January 2025). This is a working summary.

§TopicRulesIn one line
1Words1.1–1.14 Approved words only, correct part of speech and meaning. Technical names and verbs follow categories. American spelling.
2Multi-word nouns2.1–2.3 Max 3 words. Longer terms get hyphens or a full explanation. Use articles before nouns.
3Verbs3.1–3.7 Six approved forms. No unapproved tenses. Active voice. Prefer a verb over a noun for an action.
4Sentences4.1–4.4 One topic per sentence. Never omit words. Use tables for complex text. Join related sentences with connecting words.
5Procedures5.1–5.5 Max 20 words. One instruction per sentence. Imperative verb. Conditions come first with a comma.
6Descriptive writing6.1–6.8 Max 25 words. Max 6 sentences per paragraph. Topic sentence first. Vary constructions. Present complex ideas slowly.
7Warnings and notes7.1–7.6 Start with a clear command. Be specific. Conditions come first. Notes give information, not commands.
8Punctuation and counts8.1–8.11 Colons and dashes for tables. Hyphens join. Parentheses for references. Numbers and abbreviations count as one word. No semicolons.
9Writing practices9.1–9.3 Rewrite with a new construction when word-for-word is not enough. Keep dictionary meanings inside phrases. Use the dictionary correctly.
Rule people forget

Rule 4.2: Do not omit words to make sentences shorter. Shortcuts like "Can be a maximum five inches long" are non-STE. Write "Cracks can have a maximum length of five inches." Completeness beats brevity.

04Why it works with LLMs

LLMs default to fluent, hedge-heavy, synonym-rich prose. That style is hard to translate, hard to test, and easy to misread. STE pushes the model into a narrow channel. The channel is good for readers and good for downstream tools.

What STE forces the model to do

  • Cut hedging. Only can and must survive. "Might," "could," and "should" disappear.
  • Name the actor. Active voice makes the subject explicit. No hidden agents.
  • One claim per sentence. The model cannot pile three ideas into one line.
  • Pick one word per concept. Synonym drift across a long answer stops.
  • Hit a hard length cap. The model must split or cut. It cannot ramble past 20 or 25 words.

What STE gives you downstream

  • Machine translation treats each approved word the same way each time.
  • Readers with limited English reach the same meaning.
  • Reviewers check compliance with a testable list, not taste.
  • Consistency holds across a team or a set of documents.
Typical LLM default

"It's worth noting that the system might occasionally fail to initialize properly, which could potentially lead to degraded performance under certain circumstances."

30 words · passive hedge · vague · synonyms
Same content in STE style

"The system can fail at start. When it fails, the system works at a lower speed. Do the start test before you use the system."

27 words · active · concrete · one topic each

05How to ask for it

Do not just say "write in simple English." Name the standard. Give the hard limits. Ask the model to classify its own text as procedural or descriptive before it writes.

# Full-compliance prompt Write the following explanation in ASD-STE100 Simplified Technical English. Rules you must obey: - Classify the text first as procedural or descriptive. Do not mix them in one passage. - Procedural sentences: maximum 20 words. Descriptive sentences: maximum 25 words. - Maximum 6 sentences per paragraph. One topic per paragraph. Topic sentence first. - Use active voice. In procedures, always active. In descriptions, active unless the agent is unknown. - Use only these verb forms: infinitive, imperative, simple present, simple past, future, past participle as adjective. - Use only the modals "can" and "must". Do not use may, might, could, should, would, shall. - One instruction per sentence in procedures. One topic per sentence in descriptions. - Multi-word nouns: maximum 3 words. Longer terms: rewrite with of, on, in, for. - No semicolons. Do not omit words to make sentences short. - Prefer one approved word per meaning. Do not use synonyms for variety. - Keep every fact from the source. Do not add agents, numbers, causes, or obligations. After the text, list any word you could not verify against the approved dictionary and say why you kept it. Source: {paste source text here}

Why this prompt shape works

  1. Name the standard. "ASD-STE100" loads the right constraint set. "Simple English" does not.
  2. State the hard numbers. 20, 25, 6, 3. Models follow explicit caps better than vague goals.
  3. Force a classification first. Procedural and descriptive rules differ. Mixing them breaks compliance.
  4. Require a word audit. The model flags terms it could not verify. You then check those terms yourself.
  5. Protect meaning. The "keep every fact" line blocks silent deletions made only to hit a word count.
Two-pass variant

First pass: "List every proposition in this source as one line each." Second pass: "Rewrite these propositions in ASD-STE100. Keep every line. Split sentences, never delete content." This order makes meaning loss visible.

06The 80% softening

Full STE is stringent. For blog posts, READMEs, and study notes, strict compliance can sound stiff. A common working compromise is about 80% of the way to ASD-STE100. Keep the structural rules. Bend the vocabulary rules a little.

8 / 10 — structural rules kept, vocabulary relaxed

Keep these (the high-value rules)

RuleWhy keep it
Sentence length caps (20 / 25) Biggest readability win. Easy to check.
Max 6 sentences per paragraph Forces structure without sounding odd.
Active voice Removes hidden agents and ambiguity.
One topic per sentence Stops dense, compound claims.
No semicolons Cheap rule, real clarity gain.
Modals: can / must only Cuts hedge fog. Works well in technical prose.
No omitted subjects or objects Blocks telegraphic fragments.
Meaning fidelity Never sacrifice a fact to hit a word count.

Relax these (the low-value or high-cost rules)

RuleHow to relax it
Approved dictionary only Allow normal common words. Ban only true jargon and unexplained synonyms. Aim for one word per concept, not one word from a fixed list.
Six verb forms only Allow present perfect when it is the natural form ("The system has three states"). Still ban progressive ("is checking") and past perfect.
American spelling only Pick one variety and stay consistent. Do not mix.
Technical names/verbs categories Allow normal field terms without formal category paperwork.
Word-count edge cases Do not argue about hyphens and parentheses. Count by eye with a 20/25 target, plus or minus a word.

A soft prompt (about 80%)

# Softened prompt Write the explanation in a style that is about 80% of the way to ASD-STE100 Simplified Technical English. Keep these rules exactly: - Maximum 20 words per procedural sentence. Maximum 25 words per descriptive sentence. - Maximum 6 sentences per paragraph. One topic per paragraph. Topic sentence first. - Active voice as the default. - One topic per sentence. One instruction per sentence in steps. - No semicolons. Do not drop subjects or objects. - Use only "can" and "must" for possibility and obligation. - Keep every fact from the source. Split long sentences. Never delete content to save words. Soften these rules: - You may use normal common words, not only the approved STE dictionary. - You may use the present perfect when it reads naturally. - Keep one consistent word for each concept. Do not switch synonyms. Classify the text as procedural or descriptive first, then write it.
Rule of thumb

If a rule changes structure, keep it. If a rule only changes the word list, you may relax it. Structure is what readers feel. Vocabulary purity is what auditors check.

07A quick self-check

Run this pass on any answer you plan to keep. Each line is one test.

#CheckPass looks like
1Text type Procedural or descriptive. Not mixed in one passage.
2Sentence length No procedural sentence over 20 words. No descriptive sentence over 25.
3Paragraph No paragraph over 6 sentences. Topic sentence first.
4Voice Active by default. Passive only when the agent is unknown.
5Verbs No progressive. No past perfect. Modals only can / must.
6Nouns No noun cluster over 3 words. One name per thing, used everywhere.
7Punctuation No semicolons. No omitted words for brevity.
8Meaning Every fact from the source is present. Nothing new was invented.
9Hedges No "might," "could," "should," "would" unless you deliberately relaxed this.
10Consistency Same word for the same concept in the whole answer.

08Limits and caveats of STE

  • Not a full grammar guide. STE sits next to your house style and publication specs. It does not replace them.
  • Does not cover formatting. Type, numbering, units, and layout come from other specs.
  • Dictionary access matters. Full compliance needs the official Part 2 dictionary. Without it, aim for the 80% level and say so.
  • Models over-claim compliance. An LLM can say "this is STE" and still break rules. Run the self-check yourself.
  • Meaning loss is the real risk. A rewrite can pass every word rule and still drop a fact. Check fidelity first, then words.
  • Soft mode is a choice, not a cheat. Use full STE for regulated or translated docs. Use 80% for notes, blogs, and internal docs where stiffness costs more than purity gains.
Practical default

Ask for full ASD-STE100 when the output must be checked, translated, or read by non-native speakers under stress. Ask for the 80% soft version when the output is a study note, a README section, or an explanation you will edit by hand. In both modes, run the 10-point self-check before you keep the text.

09Bourbon: what was built

This part is a worked example. It explains a Go codebase in STE style. It also tells you how to read the code.

This project is a Go implementation of the Bourbon paper (arXiv:2005.14213). The paper adds learned indexes to a Log-Structured Merge Tree (LSM tree). The system keeps the WiscKey design for values. It adds Greedy-PLR models for key positions. It also adds a cost-benefit analyzer. The analyzer decides when to train a model.

The system does three jobs:

  1. Store key-value pairs at high write speed.
  2. Read values with two paths: a baseline path and a model path.
  3. Learn a model per SSTable file when the model pays for its cost.

Words you will see

WordMeaning in this codebase
LSM treeA tree of sorted string tables (SSTables) in levels.
SSTableA sorted, immutable file on disk.
MemtableAn in-memory table that accepts new writes.
WALWrite-ahead log. It records writes before they hit disk.
Value logA separate log that stores large values.
Value pointerAn address into the value log: log ID, offset, size.
PLRPiecewise linear regression. It maps a key to a position.
ModelA trained PLR. It predicts where a key sits in a file.
CBACost-benefit analyzer. It decides if training is worth it.
Delta (δ)The error bound of a model. Default is 8.
LevelA tier in the LSM tree: L0, L1, L2, and so on.
CompactionThe act of merge files into a lower level.
TombstoneA delete marker. It hides an older value.

  6. lsm/lsm.go — the glue. Start with Get, then Put.
  7. learn/learn.go — when and how to train.
  8. bench/ and cmd/ — how to run and measure.

File format

An SSTable file has four parts in order.

PartContents
Data block(s) Sorted records: 8-byte key + 16-byte value pointer.
Index block One entry per data block: first key, max key, offset, size, record count.
Filter block Bloom filter over all keys.
Footer Magic number 0x424f5552, offsets for index and filter.

Record size is fixed at 24 bytes. Fixed size makes chunk loads exact. The model can compute a byte range from a record position.

10Write path and read paths

Write path

Follow a Put from start to end.

  1. The caller runs db.Put(key, value).
  2. lsm.DB.write appends the pair to the WAL.
  3. lsm.DB.write appends the pair to the memtable.
  4. The value goes to the value log. The memtable stores a pointer.
  5. When the memtable is full, a worker flushes it.
  6. The flush writes a new SSTable in L0.
  7. The flush links the file into the level list.
  8. The old memtable stays readable until the link is complete.
  9. Compaction later merges L0 files into L1, then L1 into L2.

Delete works the same way. It writes a tombstone pointer. The tombstone hides older values during reads and compaction.

Key write functions
  • lsm.DB.Put — public write entry.
  • lsm.DB.write — WAL, memtable, value log.
  • lsm.DB.flushImm — memtable to SSTable.
  • lsm.DB.compact, mergeFiles — level merges.
Key read functions
  • lsm.DB.Get — public read entry.
  • lsm.DB.findFiles — candidate SSTables.
  • lsm.DB.lookupFile — one internal lookup.
  • sstable.Reader.Get — baseline path.
  • sstable.Reader.GetWithModel — model path.

Read path — baseline

The baseline path does not use a model. It works like WiscKey.

  1. The caller runs db.Get(key).
  2. The memtable checks the key. Hit means done.
  3. The immutable memtable checks the key. Hit means done.
  4. db.findFiles collects candidate SSTables. Newest level first.
  5. For each candidate, db.lookupFile runs an internal lookup.
  6. Reader.Get checks the bloom filter. A miss skips the file.
  7. Reader.findBlock binary-searches the index block.
  8. The reader loads the data block.
  9. searchInBlock binary-searches inside the block.
  10. A hit returns a value pointer. The reader fetches the value from the value log.

Read path — model

The model path replaces step 7 and step 8 with a learned prediction. The paper calls this the Bourbon lookup.

  1. Steps 1 to 6 are the same as the baseline path.
  2. Reader.GetWithModel runs when the file has a model.
  3. The model predicts a position p and a window [p-δ, p+δ].
  4. blockForPos maps the position to a block index. A prefix-sum binary search does this job.
  5. LoadChunk reads only the byte range for the window. It does not load the whole block.
  6. searchChunk probes the middle of the chunk first. Then it runs a binary search.
  7. On a miss, the reader loads the full block. Then it checks the adjacent blocks.
  8. On a still-miss, the reader falls back to Reader.Get. This keeps the result correct when model error exceeds δ.
Baseline cost

Binary search on the index, then load a full data block, then binary search inside the block. About 1355 ns per lookup on one file of 200,000 keys.

Model path cost

Predict a position, load a small chunk, probe and search. About 622 ns per lookup on the same file. Falls back to baseline when the window misses.

11The model and learning modes

How the model trains

plr.Train(keys, delta) builds a model from sorted keys.

The trainer keeps one open segment. Each new point must fit the current line within δ. The trainer does not use a fixed line through two endpoints. That method lets error drift. Instead, the trainer keeps a feasible slope interval. Each point intersects the interval. An empty interval closes the segment and starts a new one.

The result: every training point has error at most δ (plus rounding).

Key model functions
  • plr.Train — the training entry.
  • plr.Trainer.Add — absorb or close.
  • plr.Trainer.slopeBounds — feasible slope for one point.
  • plr.Model.Predict — position and window.
  • plr.Model.SegmentIndex — which segment covers a key.
Key learning functions
  • learn.Manager.RegisterFile — enroll a file.
  • learn.Manager.Start / Stop — background loop.
  • learn.EstimateBenefit — benefit estimate.
  • learn.Manager.TrainCost — cost estimate.
  • lsm.DB.registerLearner — wire file to manager.

Learning modes

The learn.Manager decides when to train. Three modes exist.

ModeBehavior
never No training. All reads use the baseline path.
always Train every registered file after T_wait.
cba Train only when benefit exceeds cost.

The cost-benefit analyzer (CBA) estimates two numbers for each file.

  • Cost: train time for that file. The manager calibrates time per point.
  • Benefit: how many baseline lookups a model would skip or speed up.

If benefit is greater than cost, the manager trains. If not, it skips. A bootstrap rule forces the first few files to train. This gives the manager data to compare.

12How to navigate the code

First session (about 30 minutes)

  1. Open plr/plr.go. Read Train, Add, Predict. Run go test ./plr/ -v.
  2. Open bloom/bloom.go. Read New, Add, MayContain. Run go test ./bloom/ -v.
  3. Open lsm/lsm.go. Read Options, Open, Put, Get. Do not read compaction yet.

Second session (about 45 minutes)

  1. Open memtable/memtable.go. Read Put, Get, WAL.AppendPut.
  2. Open vlog/vlog.go. Read Append, Read, ValuePointer.
  3. Open sstable/sstable.go. Read Writer.Add, Writer.Finish, Reader.Get.
  4. Trace one Put by hand. Write the call chain on paper.

Third session (about 60 minutes)

  1. Read lsm.DB.flushImm. Follow one flush from memtable to file.
  2. Read lsm.DB.compact and mergeFiles. Follow one merge.
  3. Read sstable.Reader.GetWithModel in full. Compare it with Reader.Get.
  4. Read learn.Manager loop. Connect training to SetModel.

Run and measure

Datasets for the CLI: linear, seg1, seg10, normal, random. Modes: always, cba, never.

Limits of this system
  • Single process. No network, no replication, no transactions.
  • Keys are uint64. Values are byte slices.
  • One writer at a time. Reads are safe during writes.
  • Compaction is simple. It merges whole levels. It has no size tiers.
  • The value log has no GC yet. Deleted values stay until compaction drops them.
  • The CBA uses estimates. It does not profile real lookups.
  • The model is in memory. It does not persist across restarts.

14Change checklist

  1. State the change in one sentence.
  2. Name the package you will edit.
  3. Write or extend a test first.
  4. Make the change. Keep sentences in comments short. Use active voice.
  5. Run gofmt -w . and go vet ./....
  6. Run go test ./... -count=1.
  7. If the change touches lookups, run the CLI comparison.
  8. Update REPORT.md and this page if the navigation advice becomes wrong.
